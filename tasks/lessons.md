## 2026-04-17 — Next.js 16 deprecates `middleware.ts` in favor of `proxy.ts`

- **Context:** Wiring `@supabase/ssr` session refresh during `tripplanner-688` (scaffold). Followed the official `@supabase/ssr` quickstart and dropped a `middleware.ts` at the repo root that called `updateSession`.
- **Mistake:** On Next.js **16+**, having both `middleware.ts` and `proxy.ts` (or even just `middleware.ts` if `proxy.ts` is the new convention) crashes the dev server with `Error: Both middleware file "./middleware.ts" and proxy file "./proxy.ts" are detected. Please use "./proxy.ts" only.` The page rendered as a 404 with `unhandledRejection` errors in the dev log.
- **Correction:** Next.js 16 renamed the root request-interceptor file from `middleware.ts` to `proxy.ts`, with the exported function renamed from `middleware` to `proxy`. The `config.matcher` shape is unchanged. Killed the dev server, removed `.next/`, renamed the file, renamed the export, and updated **all** documentation references that still said `middleware.ts` (README, AGENTS, product-engineering, the new `typescript-react.mdc` rule, ADR 0001, and the helper at `lib/supabase/middleware.ts` whose comment still pointed agents at the old filename).
- **Generalization:** When following any third-party "Next.js" quickstart on Next.js 16+, search for `middleware.ts` and assume it should be `proxy.ts` (function `proxy`) at the root. Update internal docs in the same change so the next agent doesn't re-introduce the old name from copy-paste.
- **Followed up by:** Encoded directly in [`docs/adr/0001-framework-choice.md`](../docs/adr/0001-framework-choice.md), [`AGENTS.md`](../AGENTS.md), [`app-context/product-engineering.md`](../app-context/product-engineering.md), [`.cursor/rules/typescript-react.mdc`](../.cursor/rules/typescript-react.mdc), and [`README.md`](../README.md). No new rule needed — the convention is now baked into the docs the next agent will read first.

## 2026-04-17 — Supabase: `sb_secret_*` value behind a `NEXT_PUBLIC_*` env name = leaked credential

- **Context:** Wiring real Supabase credentials into `.env.local` for the first time (follow-up to `tripplanner-3ca`). The Supabase wizard hands out two new-style keys: `sb_publishable_*` (public, safe in browser) and `sb_secret_*` (server-only, RLS-bypass). The user pasted both, but accidentally put the **secret** key under the env var name `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
- **Mistake:** A `sb_secret_*` value behind any `NEXT_PUBLIC_*` env name is **inlined into the browser bundle by Next.js** — every visitor gets a full-database credential that bypasses RLS. The dev server had already loaded the file by the time we caught it, so the secret was on disk, in process memory, possibly in a `.next/` dev bundle, and pasted into chat twice.
- **Correction:** Stopped before any further verification. Required the user to **rotate the secret in the Supabase dashboard FIRST** (treat it as compromised), then fixed the file shape. The corrected env contract is `NEXT_PUBLIC_SUPABASE_URL` + `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (public, browser-safe) and `SUPABASE_SECRET_KEY` (server-only, **no** `NEXT_PUBLIC_` prefix). Migrated `lib/supabase/{server,client,middleware}.ts` from `NEXT_PUBLIC_SUPABASE_ANON_KEY` → `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Tightened the boundary `rg` check to also catch literal `sb_secret_` strings: `rg -n 'SUPABASE_SECRET_KEY|SUPABASE_SERVICE_ROLE_KEY|sb_secret_' app/ components/ lib/ proxy.ts`. Nuked `.next/` to drop any cached bundle that might have included the bad value.
- **Generalization:** Two paired rules to internalize: (1) **No secret-shaped value (`sb_secret_*`, `service_role` JWT, payment provider secret, webhook signing key, etc.) ever appears behind a `NEXT_PUBLIC_*` env name.** Period. (2) **`NEXT_PUBLIC_*` is a one-way door.** Treat anything under that prefix as if it were already on a public CDN — because, in production, it is. When a leak happens, **rotate first, rename the env var second.**
- **Followed up by:** [`.cursor/rules/supabase-security.mdc`](../.cursor/rules/supabase-security.mdc) (rewritten "API keys" section with both naming systems + the inline-into-bundle warning), [`.cursor/rules/typescript-react.mdc`](../.cursor/rules/typescript-react.mdc) (boundary `rg` extended to cover `SUPABASE_SECRET_KEY` and `sb_secret_` literals), [`.cursor/skills/project-supabase/SKILL.md`](../.cursor/skills/project-supabase/SKILL.md) (env-vars table), [`.cursor/skills/project-architecture/SKILL.md`](../.cursor/skills/project-architecture/SKILL.md), [`app-context/product-engineering.md`](../app-context/product-engineering.md), [`.env.local.example`](../.env.local.example), and the three `lib/supabase/*.ts` helpers.

## 2026-04-18 — Vision pivots are an explicit chunk — overhaul docs/rules/skills/Beads in one go before any feature code

- **Context:** Mid-session, the founder's product framing changed from "Jettison is a transactional group-payments app, social explicitly OUT of MVP" to "Jettison is a social network for group travel, with payments built in." This is not a feature; it's a shift in **what the product is**. The first instinct (mine) was to immediately scope the first social Bead. The user (correctly) wanted the vision pivot to land coherently across the whole context layer first.
- **Mistake:** Treating a vision pivot like a normal feature chunk — file one Bead, write code, sort the docs out later. That path leaves stale "social is OUT of MVP" sentences in `AGENTS.md`, `product-engineering.md`, the domain skill, the PM skill, and the architecture skill, plus a Beads backlog that still reflects the old vision. The next agent (or me, next session) then reads a contradictory story: the new code says one thing, the rules and skills say another. The contradiction silently blocks correct decision-making for weeks.
- **Correction:** Treat a vision pivot as **its own chunk**, with **no feature code**, that touches every doc / rule / skill / ADR / Beads issue affected by the new framing in one coherent pass. The chunk's deliverables are: an ADR that records the decision and the alternatives; a rewritten one-liner in `AGENTS.md`; expanded MVP scope + glossary in `product-engineering.md`; updated user stories + IN/OUT examples + open-decisions list across the skills; updated hard rules across the security and review-checklist rules; a new Beads epic + sub-tasks + dep graph reflecting the new MVP, plus a Phase 2 epic with explicit gate criteria for anything deferred. Then — and only then — feature work begins. The proof checks include `rg` sweeps for stale phrasings (e.g. `rg "social feed.*out of (MVP|scope)"`) so leftover sentences don't survive.
- **Generalization:** **Vision-level changes get a dedicated docs+rules+skills+Beads chunk before any code.** The signals that a change is vision-level (vs feature-level): the one-liner in `AGENTS.md` no longer fits; the MVP loop description no longer fits; new entities appear in the domain glossary; new hard rules appear in the security layer; the OUT list shrinks materially. Any one of these triggers a new ADR + a "vision pivot" chunk. The chunk's hard rule for itself: **no feature code lands in the same commit as the pivot.** Doc + Beads commit ships first, feature work follows in subsequent chunks against the new Beads.
- **Followed up by:** [`docs/adr/0002-social-vision-pivot.md`](../docs/adr/0002-social-vision-pivot.md), [`AGENTS.md`](../AGENTS.md), [`app-context/product-engineering.md`](../app-context/product-engineering.md), [`app-context/initial-app-idea.md`](../app-context/initial-app-idea.md) (historical note added at top), the four lens skills (`project-architecture`, `project-pm`, `project-ui-ux`, `project-domain`), four rules (`supabase-security.mdc`, `project-review-checklist-sql.mdc`, `project-creative-design.mdc`, `project-core.mdc`), Beads epic `tripplanner-s3a` + 20 sub-tasks, AI follow-up `tripplanner-45u`, Phase 2 epic `tripplanner-9sp` + 6 sub-tasks, and notes appended to existing `tripplanner-bah` and `tripplanner-581`.

## 2026-04-19 — Bead title scope vs infrastructure dependencies — ship the substrate, file the dependent slice

- **Context:** Picking up [`tripplanner-s3a.1`](#) — _feat: profiles + handles + avatars_. The Bead title and description listed avatars in scope, but the AC required avatars to route through the `images-pending` bucket and the standard pre-moderation pipeline ([`.cursor/rules/supabase-security.mdc`](../.cursor/rules/supabase-security.mdc) hard rule #2). That pipeline ships in [`tripplanner-s3a.4`](#) (`infra: photo storage pipeline`), and the human-approval gate is the P0 [`tripplanner-s3a.5`](#) (CSAM) + [`tripplanner-s3a.6`](#) (moderator queue UI). Strictly reading the AC made avatars un-shippable in this chunk without either pulling three more Beads forward or building a manual-SQL approval shim that violates the spirit of the hard rule.
- **Mistake:** Tempting first move was to negotiate a partial implementation — e.g. add a `profiles.avatar_image_id uuid` column with no FK now, then "we'll wire it up properly later." That column would be dead weight: nothing in the schema enforces it, the upload UI doesn't exist, and the next agent landing `s3a.4` would have to reconcile a half-defined contract (FK target? on-delete behavior? RLS?) under pressure inside the wrong chunk. Worse, sneaking even partial avatar UI in would make the hard rule *look* satisfied without the moderator queue actually existing.
- **Correction:** Cut avatars cleanly, file the dependent slice as a follow-up Bead with a real dependency. Filed [`tripplanner-s3a.21`](#) (_feat: avatar upload UI + profiles.avatar_image_id FK_, P1, parent `s3a`, blocked-by `s3a.4`) with full acceptance criteria. Appended a scope-split note to `s3a.1`'s body so the historical record explains why avatars aren't in this commit. Reframed `s3a.1` as "the Profile entity," which is exactly what's shippable today.
- **Generalization:** When a Bead's title implies scope X but X depends on infrastructure that hasn't shipped, **ship the substrate (the part that's unblocked today), file the dependent slice as a follow-up Bead with a real `--blocked-by` link**, and update the original Bead's body to record the split. Never invent a half-defined column, half-wired UI, or "we'll add it later" placeholder just to keep the title honest. The Beads dependency graph exists exactly so we can split work along the actual seams instead of jamming it into the seams the title suggested.
- **Followed up by:** [`tripplanner-s3a.21`](#) created with full AC and dep on [`tripplanner-s3a.4`](#); scope-split note appended to [`tripplanner-s3a.1`](#); [`tripplanner-bah`](#) closed as superseded with pointer to the new richer migration. No new rule needed — the [`project-pm`](../.cursor/skills/project-pm/SKILL.md) and [`project-architecture`](../.cursor/skills/project-architecture/SKILL.md) skills already endorse scope cuts; this entry just makes the seam-finding heuristic explicit.

## 2026-04-19 — Pure-substrate chunks ship dead code; default to the smallest end-to-end slice

- **Context:** Picking up [`tripplanner-s3a.2`](#) — _feat: follow graph (asymmetric)_. Initial plan was substrate-only (table + RLS + `lib/follows.ts` server actions, no UI), with the Follow button + profile pages deferred to a follow-up Bead. The reasoning was clean: profile pages at `/[handle]` don't exist, the social-surface design system (`s3a.18`) hasn't shipped, so there's "nowhere to wire a Follow button." The user pushed back on the plan with a different lens: that's substrate that nobody can _see_ working, and the chunk would close on `pnpm tsc` + `pnpm lint` green checks alone — no proof of life.
- **Mistake:** Defaulting to substrate-only because the obvious UI destination (profile pages) wasn't ready. That framing is correct **only** if there's no other UI surface where the new server actions can be exercised end-to-end. In this case there absolutely was: the existing home page already had a greeting + signed-in state, so adding a `N followers · M following` line and a `People to follow` section listing other discoverable profiles with a Follow toggle was a small, real surface. Without it, the chunk would have closed with zero evidence that RLS, the follow actions, and the `revalidatePath` round-trip actually work in a browser.
- **Correction:** Expanded the plan to ship the substrate **plus** the smallest end-to-end UI slice that exercises every new server action: `<FollowButton />` client component, `app/_actions/follows-actions.ts` server-action wrappers (`revalidatePath('/')` lives here so the pure data layer in `lib/` stays reusable), home-page integration with `Promise.all` for counts + discover list, real empty-state copy. The meatier UI piece (profile pages at `/[handle]`) still went to the follow-up Bead `s3a.22`, but `s3a.22` was reframed as "reuses `<FollowButton />` from s3a.2" — so the work in this chunk isn't duplicated later, it's a shared component.
- **Generalization:** **Default to the smallest end-to-end slice, not pure substrate.** A chunk should ship some surface a person can poke at, even if the polished destination is in a follow-up Bead. The seam-finding lesson from `s3a.1` still applies (don't pull dependent infrastructure forward), but its corollary is: if there's _any_ existing UI surface where the new substrate can be exercised cheaply, wire it up. Pure-substrate chunks should be reserved for cases where literally no UI surface can exercise the new code (e.g. a SQL function consumed only by future migrations). Watch for the framing "nowhere to wire X" — that's usually code for "nowhere _ideal_ to wire X," and the not-ideal-but-real surface is often right there.
- **Followed up by:** Plan revised in [`.cursor/plans/follows_asymmetric_graph_ea294bdc.plan.md`](../.cursor/plans/follows_asymmetric_graph_ea294bdc.plan.md). Follow-up Bead [`tripplanner-s3a.22`](#) (_feat: profile pages at /[handle]_) created with explicit "reuses FollowButton from s3a.2" framing in title + body. No new rule needed; this is a heuristic refinement, not a hard rule.

## 2026-04-19 — Parallel chunks need a strict file-scope contract, pre-allocated migration timestamps, and a deferred-orchestration rule

- **Context:** User asked for "at least 3 tasks in parallel, but you must create a thorough plan for each first then tasks subagents." Picked [`tripplanner-s3a.16`](#) (blocks + mutes), [`tripplanner-s3a.17`](#) (legal pages + footer), and [`tripplanner-s3a.14`](#) (rate-limit primitive) — three substrate Beads with relatively low coupling. Wrote per-chunk plan files under [`.cursor/plans/`](../.cursor/plans/), then launched three subagents in a single message. The chunks shipped cleanly, but two seams almost bit us.
- **Mistake — seam #1: migration immutability.** The s3a.16 subagent, while implementing the bidirectional block check, **edited comments inside the historical [`supabase/migrations/20260419045026_follows.sql`](../supabase/migrations/20260419045026_follows.sql)** to mark its `TODO(s3a.16)` seam closed — well-intentioned, but disastrous. Modifying an already-applied migration changes its file hash and would produce a `supabase db push` error on every other developer's machine and in CI on the next push. The subagent had no rule explicitly forbidding edits to historical migrations, only the broader project-supabase skill that talks about new migrations.
- **Mistake — seam #2: implicit "stop before orchestration" rule.** The first parallel-launch prompt did not explicitly tell the subagents to stop **before** `supabase db push`, type regen, or commits. If two subagents had concurrently called `supabase db push` against the linked project (or, worse, both regenerated `database.types.ts` from different post-states), the result would have been a corrupted shared file at minimum and a wedged remote DB at worst.
- **Mistake — seam #3: temporary type workarounds left in place.** Both `lib/blocks.ts` (an `AugmentedDatabase` type) and `lib/rate-limit.ts` (a local RPC client cast) carried temporary type-narrowing because their migration's regenerated types weren't available at code-write time. Easy to forget to remove these once `database.types.ts` lands; if left in, they shadow the real generated types and silently mask future schema drift.
- **Correction:** (1) Reverted the historical-migration edit immediately with `git checkout HEAD --`, then closed the seam at the DB level by drop-and-recreating the offending policy inside the **new** s3a.16 migration. The new migration's header comment now records why the historical TODO is intentionally left in place. (2) Added an explicit "stop before push / regen / commit — orchestration is the parent agent's responsibility" line to the per-chunk subagent prompts. The parent agent then sequenced `supabase db push --linked` (s3a.16 then s3a.14, in order) → `supabase gen types typescript --linked > database.types.ts` once → cleanup of the temporary type augmentations → `tsc + lint`. (3) Pre-allocated non-conflicting migration timestamps (`20260419050000` and `20260419050100`) before launching subagents so the two database-touching chunks couldn't collide on filenames.
- **Generalization:** When running ≥2 chunks in parallel: (a) **enforce strict file-scope contracts** — each subagent gets an explicit list of files it owns and a list of files it must not touch (especially anything under `supabase/migrations/` that already exists; historical migrations are immutable once applied); (b) **pre-allocate migration timestamps** so concurrent migrations cannot collide on filenames; (c) **subagents stop before orchestration** — they implement, run local typecheck/lint, and report back; the parent agent runs `supabase db push`, type regen, temp-type cleanup, and commits sequentially in dependency order; (d) **always leave a follow-up `bd` Bead for any AC line that was honest-deferred because of file-overlap with a parallel chunk** (e.g. `s3a.14`'s "wire to Follows" was honest-deferred because s3a.16's `follow-actions.ts` neighborhood was in flight); (e) **temporary type workarounds get removed in the same orchestration pass that regenerates types** — never carried into a commit.
- **Followed up by:** This lesson; the migration-immutability point should be promoted to the [`project-supabase`](../.cursor/skills/project-supabase/SKILL.md) skill the next time it's edited (a one-line "historical migrations are immutable; close cross-chunk seams in a new migration" addition is enough). The subagent-stops-before-orchestration rule should be promoted to a [`project-orchestration`](../.cursor/skills/project-orchestration/SKILL.md) addition the next time it's edited. No file-overlap collision actually occurred this run; the contract held. New Beads filed: [`tripplanner-s3a.23`](#), [`tripplanner-s3a.24`](#), [`tripplanner-s3a.25`](#) — each carries a `--discovered-from` line back to the chunk that surfaced it.
